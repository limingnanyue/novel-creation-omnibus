# 小说审计工作流（audit-workflow）

> 来源：集成自 novel-audit-v6.0.0 专家面板架构
> 触发词：审计、审稿、体检、诊断、找问题、专家会诊、多视角审查、质量评估

---

## 1. 何时用这个模块

- 写完一章/一卷后想全面体检（不只是去AI味，还要查剧情/人设/一致性/商业）
- 读者反馈"哪里不对劲"但说不清具体问题
- 修改前需要定位"最该先改什么"（避免盲改）
- 长篇连载中途想检查是否出现断层/伏笔失约/人设崩塌

---

## 2. 五专家面板（E1-E5）

> 纯 prompt 角色卡，主 Agent 串行扮演（solo 模式）。每轮只戴一顶帽子，互不污染。

| 专家 | 职责 | 核心维度 | 必做动作 |
|:-----|:-----|:---------|:---------|
| **E1 语感与去AI味** | 语气/节奏/同义/人感 | D1语气 D7节奏 D8场景 D9世界观 D20人感 | 逐句审查，每句标 passed/failed |
| **E2 剧情与钩子** | 剧情/伏笔/爽点/悬念/金手指 | D2剧情 D10爽点 D11悬念 D15金手指 | 判钩子真假、爽点密度、伪因果 |
| **E3 人物与对白** | 人物弧光/深度/MBTI/对白 | D3人物 D12对白 | 查角色走形、动机支撑 |
| **E4 跨章一致性** | 事实/时间线/道具/开篇结构 | D4一致性 D13开篇 | 8类CT门禁（最高优先级） |
| **E5 商业化与整体** | 平台适配/留存/整体节奏 | D5商业 D6全局 | 平台rubric、4维评分 |

**硬约束**：E4 事实一致性判定优先于任何剧情/人设/节奏建议。其他专家建议若破坏事实一致性，必须让路。

## 3. 11 维评估矩阵（打分用）

> 来源：`llm_evaluator_11d.json`（v1.4）。总权重=1.00。
> 注意：这里的 E1-E11 是评估维度编号，与上面专家编号 E1-E5 不同（命名空间隔离）。

| 维度 | 标签 | 权重 | 归属专家 |
|:-----|:-----|:-----|:---------|
| 语气一致性 | tone | **0.10** | E1 |
| 视角稳定性 | pov | **0.10** | E1 |
| 角色好感度 | likeability | 0.08 | E3 |
| 节奏感 | pacing | 0.08 | E1/E5 |
| 对白自然度 | dialogue_naturalness | **0.10** | E1/E3 |
| 描写质量 | description_quality | 0.08 | E1 |
| 情感共鸣 | emotional_resonance | **0.10** | E3 |
| 世界观一致 | world_consistency | **0.10** | E4 |
| 剧情推进 | plot_advancement | **0.10** | E2 |
| 读者钩子 | reader_hook | 0.08 | E2/E5 |
| 商业吸引力 | commercial_appeal | 0.08 | E5 |

**第一梯队（0.10，6项）**：语气、视角、对白、情感、世界观、剧情——"写得好不好"的硬核
**第二梯队（0.08，5项）**：好感度、节奏、描写、钩子、商业——"卖得好不好"的软指标

每维度 1-5 分打分，加权汇总。低于 3.5 的维度列入必改清单。

## 4. 审计流程（6 阶段）

### Phase 0：专家独立审读
- 每位专家只看自己负责维度的清单切片 + 相关正文
- **不投喂全维度全量，不投喂其他专家结论**（避免被框死）
- 输出 5 份结构化 findings（severity S1-S4 + 证据 + 修复方向 + 置信度）

### Phase 1：代码层辅助校验
- 跑 `word-count-tool.py`（对话比/AI味密度/段落分布）
- 跑 `novel-tools.py --check-continuity`（章首禁用词）
- 输出量化指标，作为专家判断的辅助锚点

### Phase 2：交叉审计 + 主要矛盾判定
- 按 6 个交叉区（CC1-CC6）碰撞双专家视角
- 4 条仲裁规则去重/消解/合并
- **必做**：列矛盾清单 → 标⭐主要矛盾 → 判对抗性 → 选主攻方向

### Phase 3：综合评级
- 11 维加权打分
- 每维度并列「专家分 / 代码分 / 差异解读」
- §2 按"⭐主要矛盾 → 次要矛盾（按 severity）"结构渲染

### Phase 4：修改方案（集中兵力）
- 四类方案：A精准手术 / B稳健提升 / C风格重塑 / D结构重构
- **方案首页必须标注"本次修改主攻 [Phase 2 主要矛盾]"**
- S3 级与主要矛盾无因果关联的列入"暂缓清单"——**伤其十指不如断其一指**

### Phase 5：审计自省（meta-review）
- 复盘审计本身：有没有误判？有没有遗漏？
- `misjudgments` / `omissions` 为空时必须写明"未发现，原因是…"
- 每条问题必须配一条可执行的 `fix_action`

## 5. 跨会话状态机（最关键的可靠性机制）

> **「AI 无法跨会话记忆，落盘是唯一可靠的跟进机制——你的自省不落到文件里，等于没自省。」**

### 状态落盘

每章审计完成后，将 `next_focus`（下次重点关注）落盘到项目目录：

```
.novel_state/<book-id>/meta_review_log.jsonl
```

格式：每章一条 JSONL，含：
- `chapter`：章节号
- `misjudgments`：本次误判
- `omissions`：本次遗漏
- `next_focus`：下次审计同书时要重点盯的事项
- `timestamp`：时间戳

### 下次审计时

Phase 0 启动时，读取 `meta_review_log.jsonl` 末条的 `next_focus`，注入到专家组与代码层的上下文中。这是整个体系**唯一可靠的跨会话状态传递路径**。

## 6. 降级链（保证可用性）

```
默认 → 主 Agent 串行扮演 E1→E5（solo 模式）
       → token 超限 → 仅跑代码层（word-count + check-continuity）
       → 仅做 E1 去AI味 + E4 一致性（最高优先级两项）
全程不中断
```

## 7. finding 输出格式

每条问题按统一 schema 输出：

```json
{
  "id": "E2-003",
  "expert": "E2",
  "severity": "S2",
  "dimension": "D2",
  "location": "第14章第3段",
  "evidence": "原文摘录…",
  "llm_judgment": "章末钩子是假悬念，读者已猜到答案",
  "fix_direction": "改为信息悬念：让读者不知道主角是否会发现真相",
  "confidence": 0.85
}
```

**severity 四档**
- S1：致命（事实矛盾/逻辑硬伤）→ 必须立即修
- S2：严重（影响阅读体验）→ 本轮必改
- S3：中等（可优化）→ 暂缓清单
- S4：轻微（建议）→ 记录即可

## 9. spawn / solo 双路径执行（v6.1 新增）

> 来源：novel-audit-v6.0.0 · `panel.md` v5.5.2

专家组（E1-E5）是**纯 prompt 角色卡**，必须由主 Agent 激活才能运行。激活方式有两种，**输出契约完全一致**（均走 `expert_output_schema.md`），聚合层无需区分来源。

### 9.1 双路径对照

| 路径 | 触发条件 | 行为 | 成本/速度 |
|:-----|:---------|:-----|:----------|
| `spawn`（默认并行） | 主 Agent 具备子 Agent 派生能力 | 并行派生 5 个 `general-purpose` 子 Agent，各自加载一张角色卡审读 | 快，占子 Agent 配额 |
| `solo`（降级串行） | 主 Agent **不具备**派生能力，或派生失败 | 主 Agent **自己串行扮演** E1→E5，逐个加载角色卡自审，一人分饰五角 | 慢（串行），不依赖派生能力 |

### 9.2 solo 串行纪律

每轮**只戴一顶帽子**：

1. 读取 `experts/E<n>_*.md` 全文，**切换为该专家人设**（仅承担该专家职责，不越界评其他维度）
2. 取章节正文 + 该专家负责维度的清单切片（与 spawn 完全一致的输入切片规则）
3. 以该专家视角产出符合 `expert_output_schema.md` 的 findings，`expert` 字段如实填 `E<n>`
4. E1 轮次须额外执行逐句审查（逐句阅读全文，逐句标记 passed/failed，输出 `sentence_review`）
5. 退出人设，进入下一专家

> **关键**：solo 不是"放弃专家组"，而是"换主 Agent 亲自演"。产出仍是 5 份 `expert_findings.json`，Phase 2 交叉审计 / Phase 3 聚合 / Phase 4 修改方案照常执行，双轨报告结构不变。

### 9.3 自动降级链

```
默认 → spawn（并行派生 5 个子 Agent）
       → 主 Agent 无派生能力或派生失败 → solo（串行扮演 E1-E5）
       → token 超限 → 仅跑代码层（word-count + check-continuity）
       → 仅做 E1 去AI味 + E4 一致性（最高优先级两项）
全程不中断
```

### 9.4 solo 选择规则

主 Agent 启动专家组前先自检——若当前运行时无子 Agent 工具（无 Task/Agent 派生入口），或派生调用返回失败，**自动切 solo**，**不中断、不退化为 code-only**。仅当用户显式选 `code-only` 或预算超限时才跳过专家组。

> "写得好不好"的硬核——必须 ≥ 4 分，否则触发深度复审

- **E1 语气一致性** / **E2 视角稳定性** → E1 主审
- **E5 对白自然度** → E1+E3 协同（CC1 交叉区）
- **E7 情感共鸣** → E3 主审
- **E8 世界观一致** → E4 主审（CT6 设定矛盾兜底）
- **E9 剧情推进** → E2 主审（伪因果判定）

### 10.3 第二梯队（0.08，5 项软指标）

> "卖得好不好"的软指标——低于 3.5 列入必改清单

- **E3 角色好感度** / **E4 节奏感** / **E6 描写质量** / **E10 读者钩子** / **E11 商业吸引力**

### 10.4 评分规则

- 每维度 1-5 分打分，加权汇总
- 加权总分 ≥ 4.0 = 优秀 / 3.5-4.0 = 合格 / < 3.5 = 必改
- 低于 3.5 的维度列入必改清单
- 硬门禁命中（AI 句式≥1/CT 矛盾/事实硬伤）→ 总分上限锁 3.0

## 11. Phase 0-5 详细操作清单（v6.1 强化）

### Phase 0 · 专家独立审读（先读正文，独立判断）

**输入**：① 章节正文（或分块）；② 该专家负责维度的审计内容清单切片；③ `meta_review_log.jsonl` 末条的 `next_focus`（若有）

**禁忌**：不投喂全维度全量；不投喂其他专家结论；不投喂代码层结论

**输出**：5 份符合 `expert_output_schema.md` 的 `expert_findings.json`

**E1 必做**：逐句审查（覆盖文言文/电报式6变体/AI套话/比喻排比/解说腔/节奏断点六类，每句 passed/failed）

### Phase 1 · 代码层辅助校验

**命令**：
```bash
python3 scripts/word-count-tool.py <chapter>      # 对话比/AI味密度/段落分布
python3 scripts/novel-tools.py --check-continuity <dir>  # 章首禁用词
```

**三项辅助职责**：
1. **量化校验**：为专家判断提供确定性数值对照
2. **硬门禁兜底**：AI 句式≥1 / 6+1 道门禁 / 事实矛盾——命中即记 S1/S2，**不可被专家覆盖**
3. **遗漏补查**：硬指标点若专家 findings 未涉及，自动补入并标注 `[code-supplement]`

### Phase 2 · 交叉审计 + 主要矛盾判定

**6 个交叉区**（CC1-CC6）按 `cross_cut_matrix.md` 仲裁规则去重/消歧/合并

**必做**：
- 列矛盾清单
- 标 ⭐ 主要矛盾（不是 findings 平铺）
- 判对抗性（冲突是否可调和）
- 选主攻方向（伤其十指不如断其一指）

### Phase 3 · 综合评级（双轨）

- 11 维加权打分（每维度并列「专家分 / 代码分 / 差异解读」）
- §2 按"⭐主要矛盾 → 次要矛盾（按 severity）"结构渲染
- 硬门禁命中 → 总分上限锁 3.0

### Phase 4 · 修改方案（4 类）

| 方案 | 适用 | 改动幅度 |
|:-----|:-----|:---------|
| **A 精准手术** | 个别硬伤修复 | ≤5% 字数 |
| **B 稳健提升** | 多维度优化 | 5%-15% 字数 |
| **C 风格重塑** | 整体语感问题 | 15%-30% 字数 |
| **D 结构重构** | 主要矛盾在结构层 | >30% 字数 |

**方案首页必须标注**："本次修改主攻 [Phase 2 主要矛盾]"
S3 级与主要矛盾无因果关联的列入"暂缓清单"

### Phase 5 · 审计自省（meta-review）

- 复盘审计本身：有没有误判？有没有遗漏？
- `misjudgments` / `omissions` 为空时必须写明"未发现，原因是…"
- 每条问题必须配一条可执行的 `fix_action`
- 落盘到 `.novel_state/<book-id>/meta_review_log.jsonl`

## 12. finding 完整 schema（v6.1 强化）

```json
{
  "id": "E2-003",
  "expert": "E2",
  "severity": "S2",
  "dimension": "D2",
  "location": "第14章第3段",
  "evidence": "原文摘录…",
  "llm_judgment": "章末钩子是假悬念，读者已猜到答案",
  "fix_direction": "改为信息悬念：让读者不知道主角是否会发现真相",
  "confidence": 0.85,
  "cross_cut": "CC2",
  "code_supplement": false,
  "llm_vs_code": "expert_strict",
  "exempt": false,
  "exempt_reason": null
}
```

**字段说明**：

| 字段 | 含义 |
|:-----|:-----|
| `severity` | S1 致命 / S2 严重 / S3 中等 / S4 轻微 |
| `confidence` | 0.0-1.0，专家判断置信度 |
| `cross_cut` | 涉及的交叉区（CC1-CC6），无则 null |
| `code_supplement` | 是否代码层补查（专家未涉及但硬指标点） |
| `llm_vs_code` | 专家×代码分歧：`corroborated`（一致）/ `expert_strict`（专家严）/ `code_strict`（代码严） |
| `exempt` | 是否豁免（白名单/合理理由） |
| `exempt_reason` | 豁免理由（必填 if exempt=true） |

## 13. 评分治理红线 P0（v6.2 新增）

> 来源：novel-audit-v6.0.0 · `score_governance.json`
> **优先级 P0**：审计计算完成后任何人不得修改。违反红线 = 评级操纵。

### 13.1 四条禁令

| # | 禁令 | 触发场景 |
|:---|:-----|:---------|
| 1 | **禁止覆写** | 审计计算完成后任何人（含执行审计的 agent 本人）不得手动修改、覆写任一维度分或总评分 |
| 2 | **禁止主观调分** | 不得以体感/经验/作者偏好/平台关系等主观理由调高或压低任一分数 |
| 3 | **禁止评级操纵** | 不得为让某章好看而人为拉高总评、压制低分维度，或将不合格章硬抬进及格区 |
| 4 | **禁止 LLM 覆盖确定性结果** | 主进程 LLM 只能补充 findings 的叙述与改写建议，无权用自由文本改数字 |

### 13.2 5 档评分 band

| 档位 | 分数区间 | 状态 |
|:-----|:---------|:-----|
| **A** | 90-100 | 优秀 |
| **B** | 80-89 | 良好 |
| **C** | 70-79 | 合格 |
| **D** | 60-69 | 🔒 freeze（必须整改） |
| **F** | 0-59 | 🔒 freeze（必须重写） |

### 13.3 复评纪律

- **最大复评轮数**：3 轮
- **解冻门**：复评须同脚本同阈值重跑；weighted_total≥60 且所有否决维度≥其 floor 方可解冻；封顶仍 F 转人工/作者重写
- **禁止表面修补**：F 级整改须触及根因维度
  - D1 低于 floor → 必须做去 AI 化重写（非仅删词调标点）
  - D5 低于 floor → 须补钩子/强化动机
- **禁止字段**：`manual_override` / `adjusted_by` / `human_score` 三个 key 不得出现在任何输出 JSON 中

### 13.4 硬门禁与总评联动

- AI 句式 ≥ 1 → 总分上限锁 3.0（即 D 档上限）
- CT 矛盾 ≥ 1 → 总分上限锁 2.5（即 F 档）
- 事实硬伤 ≥ 1 → 总分上限锁 2.0（即 F 档低位）
- L1-L4 任一硬门禁命中 → 总分不得进入 A/B 档

### 字段说明

| 字段 | 必填 | 说明 |
|:-----|:-----|:-----|
| `expert` | 是 | E1–E5 |
| `module` | 是 | 模块名 |
| `finding_id` | 是 | 格式 `<专家>-<3位序号>`，全局唯一 |

### severity 标尺（与代码层对齐）

- **S1**：致命，直接破坏阅读体验或硬门禁（AI 味重到出戏、事实硬矛盾）
- **S2**：重要，明显拉低质量（人物扁平、爽点缺席、钩子虚弱）
- **S3**：建议，可优化项（某段节奏偏平、某对白可更贴人设）
- **S4**：细节，锦上添花（某词可更精准）

### 逐句审查契约（E1 必执行，其余专家选执行）

> 解决脚本无法检测文言文表达和电报式简略句式的盲区。与段落功能二分法互补——段落二分法看"这段在干嘛"，逐句审查看"这句是不是人话"。

**6 类必审**：文言文表达 / 电报式简略句式 / AI 套话残留 / 比喻排比密度 / 解说腔 / 节奏断点

**纪律**：
1. 逐句阅读，不得跳读或抽样
2. 每句明确标记 passed=true/false
3. 未通过须注明问题类型及修改建议
4. `sentences` 数组长度 = 章节总句数（以句号/问号/叹号/省略号结尾的完整句），一句一条，不得合并或跳过
5. 逐句审查中发现的 S2 级问题必须同时进入 `findings` 数组（参与硬门禁判定）
6. 对白句的文言文/电报式判定标准放宽——角色说话可以短促/文绉绉，只要符合人设
7. 系统面板/图鉴 UI（【】包裹）不纳入审查范围

## 16. E3 / E5 专家完整角色卡（v6.2 集成）

### 16.1 E3 · 人物与对白专家

**角色设定**：编剧系人物塑造导师，MBTI 信徒，信仰"角色自己会走路"。不在乎章节多爽（那是 E2），在乎**书里这些人读着读着会不会在脑子里活过来**。

**主审维度**：D3 人物/对白、D12 人物深度、D20 场景矩阵

**5 大核心判断**（代码代理做不好的部分）：

1. **人物是否立得住**：是否缺印象标签、是否扁平、是否前后动机断裂
2. **对白是否贴人设**：同样的"冷峻"句式，配角说出来是 AI 味，主角说出来是性格——E3 区分得清
3. **是否在成长弧上**：角色是否有变化？还是每章原地踏步？
4. **对白潜台词**：对白是否在"说一件事、藏另一件事"？还是直白 exposition？
5. **场景身体感（D20）**：打斗读着疼不疼？情感戏是 show（"他攥紧了拳头"）还是 tell（"他很生气"）？

**交叉区职责**：
- **CC1 对白自然度 × 人设**（与 E1 共审）：主张"保留角色复杂句式展现人设"，E1 主张"去 AI 味简化"。仲裁底线：不破坏角色辨识度。E3 视角代表"人设保真"
- **CC3 人物驱动 × 剧情推进**（与 E2 共审）：判断人物动机是否支撑剧情
- **CC5 开篇钩子 × 平台留存**（与 E5 共审）：看人物共鸣/定调

**硬约束**：代码层已发现的 MBTI 不一致/对白功能率问题，引用其 finding_id，不重算；**无权否决**代码层硬门禁；尊重作者家规（如角色术语"收录"不用"记录"）

### 16.2 E5 · 商业化与整体专家

**角色设定**：平台运营 + 读者留存专家，站在"普通读者深夜刷到这一章，划走还是继续"的视角。不抠字句（E1）、不数爽点（E2）、不品人物（E3）、不查事实（E4）——只看**全局：这章整体能不能留住人、值不值得追、对不对平台胃口**。

**主审维度**：D5 整体/商业化、D6 跨 skill 附带审计、全局

**4 大核心判断**：

1. **开篇定调与留存**：前 3 段是否立刻把读者按在椅子上？定调是否清晰（读者知道这是本什么书、主角是谁、要干嘛）？
2. **整体完成度与节奏呼吸**：全章读完是"意犹未尽"还是"松一口气终于完了"？张弛是否得当（CC6 与 E1 共审）？
3. **平台适配**：番茄推流要短句快节奏+强钩子；起点男频要爽点密度；晋江要人物弧光+情感落点
4. **读者价值落点**：读完这一章读者得到了什么（情绪释放/信息/期待）？还是空手而归？

**交叉区职责**：
- **CC5 开篇钩子 × 平台留存**（与 E3/E2 共审）：判平台适配与留存，合并人物(E3)/剧情(E2)钩子质量
- **CC6 整体节奏呼吸感**（与 E1 共审）：E5 的"读者不弃读"判断**优先于** E1 的微观节奏洁癖

**硬约束**：代码层已算的平台 rubric 分、钩子缺失等，引用其 finding_id；**无权否决**代码层硬门禁；但"读者不弃读"判断在 CC5/CC6 冲突仲裁中**优先级最高**
